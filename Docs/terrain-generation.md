# 地形生成ルール 検討用引き継ぎ資料

Unrailedライク(VRChat UdonSharp)のフィールド生成に関する現行仕様・検証方法・検討論点のまとめ。
このドキュメントは「生成ルールを別セッションで検討する」ための引き継ぎ用。実装の全体像(ネットワーク同期等)は含めず、生成ルールに限定する。

## 背景: なぜこの方式か

- VRChat Udon は `Object.Instantiate` 不可 → 全オブジェクトは事前プール配置。地形は「6チャンク×24スロット」のリングバッファで無限進行を表現する
- レイアウトを `[UdonSynced]` で同期すると帯域(約11KB/s)を圧迫する → **地形は (seed, worldChunk) の純粋関数として各クライアントがローカルで決定的に再生成**し、同期するのは「採掘済みビットマップ」だけにする
- したがって生成ルールの変更は同期プロトコルに影響しないが、**乱数消費順の不変性**を壊すと既存ワールドと地形がズレるので手続き上の注意がある(後述)

## 現行アルゴリズム仕様 (v1, M2実装済み → v2ノイズ方式に置換済み。参考として残す)

実装箇所: `Assets/Scripts/ChunkManager.cs` の `GenerateChunk(int slot, int worldChunk, int seed)`

### チャンクRNGの初期化

```csharp
var rng = new System.Random(seed * 73856093 + worldChunk * 19349663 + 12345);
```

- `runSeed`: ラン開始/リセット時にマスターが `Random.Range(1, 1000000)` で抽選した `[UdonSynced]` 値
- C# int のオーバーフロー(32bit wrap)を含めて再現する必要がある(後述のPython再現参照)
- 係数(73856093, 19349663, 12345)は任意の混合定数。変更すると全地形が変わる

### スロット配置と抽選 (24スロット/チャンク)

```
for s in 0..23:
    cellX = s % 6        // x方向 6セル (セル幅4m)
    cellZ = s / 6        // z方向 4セル (セル幅5.75m)
    localX = cellX*4 + 0.8 + rng.Next(240)/100   // セル内ジッター 0〜2.4m
    localZ = -4.5 + cellZ*5.75 + rng.Next(275)/100
    roll   = rng.Next(1000)
    type   = 空
    if |localZ - 6| >= 2:              // 線路コリドー(中心z=6±2m)は障害物なし
        roll < 160  → 岩(鉄)
        roll < 500  → 木(木材)
```

- チャンクは x 24m × z 24m (zは -6〜18、線路中心 z=6 を挟む)
- スロット→セルの対応が固定なのでノード同士は物理的に重ならない
- 1スロットあたり乱数をちょうど3回消費(位置x, 位置z, 種別)。**この消費順・消費数の固定が決定性の生命線**

## 計画中の拡張仕様 (破壊不能岩・池)

→ **生成ロジックは v2 ノイズ方式に吸収・実装済み** (後述)。池・破壊不能岩のビジュアルは**仮実装(暫定プリミティブ)で運用中**(検討論点11参照)。橋の価格は木材1個で仮決め(M4b、実プレイ感触で最終確認)。

方針決定済み事項:

| 項目 | 決定 |
|---|---|
| 破壊不能岩 | 1タイル、コライダーあり(通行不可)、採掘不可、線路敷設を永続ブロック |
| 池 | 1タイル単位、歩けない(コライダーあり)、敷設は橋(木材消費)でのみ可(M3で実装) |
| 密度 | 難易度連動(ただし stationCount ではなく worldChunk の関数。下記⚠️参照) |

### 抽選式(案)

```
// 既存の3回消費の「後」に追加(既存地形をズラさないため)
if type == 空 かつ コリドー外:
    tier = worldChunk * 24 / 駅間隔タイル数(40)
    hardRockChance = min(10%, 3% + tier*1.5%)
    pondChance     = min(12%, 4% + tier*2.0%)
    roll2 = rng.Next(1000)    // ← 全スロットで必ず消費(条件式の中に書かない)
    roll2 < hr*10  → 破壊不能岩
    roll2 < (hr+po)*10 → 池
```

⚠️ **重要な不変条件**: 生成は (seed, worldChunk) の純粋関数でなければならない。
`tier` を `stationCount`(実行中に変化)から計算すると、チャンク再生成のタイミングがクライアント間でズレた際に地形が分裂する。worldChunk(≒進行距離)ベースなら常に一致する。

## v2: ノイズ方式 (ChunkManager.cs に実装済み)

プロトタイプ: `Tools/terrain_noise_proto.py` (seed=402052 で v1 位置との一致を検証済み: chunk0 Node0 (1.86, -2.79) ✓)

**Unity実装との一致検証済み**: seed=402052, wc0-9 の全240スロットで (位置, タイプ) が Python と Unity (リフレクションで `SlotPositionCm`/`ComputeTypeFromCm` を直接呼出) の出力と完全一致。

### 概要

- **位置はv1と完全に同一**: セル+ジッター、`System.Random` の1スロット3回消費を維持(3回目はダミー消費)。既存ワールドとノード位置が一致する
- **タイプ決定だけをノイズに置換**: 固定小数点Perlinノイズ(整数演算のみ、float不使用)。乱数消費順の不変性問題はタイプ決定から消える
- 原作らしい「森の塊・鉱脈・湖」がノイズのしきい値帯で自然に出る。ワールド座標でサンプルするのでチャンク境界はシームレス
- **コリドーは先頭2チャンクのみ** (スターター線路30枚=最初の駅周辺をカバー)。それ以外はコリドー無しで障害物が全zに出る = 原作の「自分で道を切り開く」体感
- **破壊不能岩は attempt ラダー + BFS経路検証** で進路封鎖を防止 (後述)

### 生成手順 (1スロットあたり)

1. 位置: xはv1と同じ `cellX*400 + 80 + Next(240)`。**zはハッシュ全展開 (flat方式)**: `lz_cm = originZcm - 1050 + cellZ*500 + hash(worldChunk, s, seed^0xD1B54A35) % 500`。セルピッチ500cmで全域に一様展開し、帯状ギャップを消す (z範囲はv1と同一の -4.5〜15.49m)。rngの3回消費 (`Next(240)`, `Next(275)`, ダミー `Next(1000)`) はx位置のv1互換のため維持
2. コリドー判定: **`worldChunk < 2` の場合のみ** `|lz_cm - originZcm| < 200` なら空 (origin.z=6m なら中心z=6±2m)
3. ノイズ入力は**座標の整数cm表現**から計算 (floatを一切使わないのが決定性の肝):
   - `px = worldChunk*2400 + lx_cm + 10000`, `pz = lz_cm + 10000` (+100m は負座標回避オフセット)
4. タイプ判定 (優先順位順):

```
water >= tW → 池
rock  >= tH → 破壊不能岩 (鉱脈のコア: 岩ノイズの高い領域)
rock  >= tR → 岩
tree  >= tT → 木
else        → 空
```

### ノイズ実装仕様 (C#/UdonSharp にそのまま移植可能)

- Q10固定小数点 (S=1024)、8勾配 `(±1,0),(0,±1),(±1,±1)`、fade `6t^5-15t^4+10t^3`
- ハッシュ (全て uint32 wrap 演算):
  ```
  h = ix*374761393 + iz*668265263 + seed*974711
  h = (h ^ (h>>13)) * 1274126177
  h ^= h >> 16
  grad = h & 7
  ```
- 正規化: `v = clamp((n + 724) * 1000 / 1448, 0, 1000)` (724 = 2D Perlin 理論最大のQ10値)
- 乗算は int64 (C# `long`) でオーバーフロー回避。シフトは算術シフト (C# と Python で一致)
- **`Mathf.PerlinNoise` は使わない**: PC/Android 間の完全一致が保証されないリスクがあるのと、整数実装なら Python 検証環境とビット一致させられるため
- レイヤーは `seed ^ layerConst` で独立化 (木 0x9E3779B9, 岩 0x3C6EF372, 水 0x7F4A7C15)

### 異方性波長 (重要)

| レイヤ | λx | λz | 狙い |
|---|---|---|---|
| 木 | 16m | 12m | チャンク内に2-3個の森の塊 |
| 岩 | 13m | 11m | 小さめの鉱脈 |
| 池 | 40m | 13m | xに長くzに狭い = 線路に沿った湖。z全幅(約20m)を塞ぐ帯状湖を防止 |

教訓2点:

- **波長はチャンク幅24mの整数倍にしない**。λ=24mで試したところ「1チャンク=1ノイズグリッドセル」になり、T19個・P11個といった全振りチャンクが出た
- **z方向のλは20m以下に**。フィールドのz全長が約20mしかないため、λz > 20mだとz方向にほぼ一定の場=帯状になる(湖が線路を全封鎖しうる)

### 密度カーブ (tier = worldChunk*24 / 駅間隔)

名目率 (非コリドーセルに対する割合):

- 木 30% + 0.75/tier (cap 36%)
- 岩 10% (フラット)
- 破壊不能岩 3% + 1.5/tier (cap 10%)

### 破壊不能岩の密度ラダーとBFS経路検証

コリドー撤廃に伴う「破壊不能岩で進路が塞がれる」問題への対策。仕組み:

- 生成は `(seed, worldChunk, attempt)` の純粋関数。attempt (0-3) はスロットごと2bitにパックして `[UdonSynced] attemptPacked` で同期
- **attemptはtHしきい値だけを変える** (率: 通常→1/2→1/4→0%)。木/岩/池は不変。attempt上昇で H→岩 に変わるだけなので**採掘済みビットマップと矛盾しない** (Hは採掘不可でマスクbitが立たないため)
- オーナーが `OwnerRecycleOldestChunk` / `OwnerResetChunks` 内で検証: BFS(起点=線路末端タイル、目標=ウィンドウ右端、通行不可=破壊不能岩のみ、池=橋・木岩=採掘で通行扱い、グリッド 144×22タイル)。不通なら「到達最大x+1列のチャンク」のattemptを+1して再検証 (上限18回、attempt3=H 0%で必ず終了)。最終attemptを `RequestSerialization` で一度だけ同期 (途中地形のチラつき無し)
- 列車位置・線路末端は実行時状態なのでクライアント側の生成条件には使えない → **検証とリトライ決定はオーナー専用、結果(attempt)だけ同期** する設計。途中参加も同期経由で正しい地形を再現

**重要な実測知見**: v1由来のセル配置 (zピッチ5.75m, ジッター最大2.75m) では隣接zセル間に最低2タイルの隙間があり「ノードが存在できないz帯」が構造的に存在したが、**flat配置への移行でこの帯は消滅**した。それでもBFSシミュレーション (200ウィンドウ/tier, 破壊不能岩のみ通行不可) は **全tierでリトライ0%** (率を55%に盛ったストレステストでも0%)。破壊不能岩がせいぜい2-3個/chunk (=タイル密度1%未満) では、24行を縦断する壁がパーコレーション的に成立しないため。つまりこの機構は「ほぼ発動しない保険」だが、flat化で壁が理論上成立しうるようになった分、保険としての意味は増えている。

### v1からの互換性

- 位置: **xは完全一致** (rng3回消費維持のおかげ)。**zはflat配置で変更** (帯解消のため)。rng消費列自体はv1と同一なので、位置生成以外でrngを使う将来拡張とも衝突しない
- タイプ: 全変更 → **世代「v2」扱い**。「既存地形を保つ微調整」ではない
- 同期プロトコル: `attemptPacked` を追加 (int 1つ)。`nodeMasks`/`baseChunk` と同じ Manual sync
- 将来レイヤー(装飾、バイオーム変調)を追加しても既存タイプ判定に影響しない = v1時代の「乱数消費順で地形がズレる」問題は構造的に解消される
- flat配置の副作用: 同じ1mタイルに2ノードが乗るケースが 0.07ペア/chunk 発生しうる (xセルはタイル空間で連続だがzは独立一様のため)。採掘・敷設判定はスロットベースで実害はなく、見た目も1m以内の近接に留まる。許容とし、気になるようなら決定的なデコリレーション処理を後追加する

## Python再現・検証環境

.NET `System.Random`(Knuth subtractive)をPythonで完全再現し、**Unity実測との一致を検証済み**:
seed=402052, chunk0, Node0 → Python (1.86, -2.79) = Unity実測 (1.86, -2.79) ✓

再現の要点(実験コードを書くときの注意):

1. `.NET System.Random` 初期化で `mk < 0` なら `+2147483647`、4ラウンドの減算でも同様の負数補正が必要(省略すると即壊れる)
2. **混合seedが負の場合、初期化 `mk = mj - mk` や減算ラウンドが int32 でオーバーフローし、.NET は unchecked で黙って wrap する**。Python 側も全算術に wrap32 (`v & 0xFFFFFFFF` → `>= 2**31` なら `-2**32`) を入れないと、SeedArray の1要素だけがズレて「散発的に1回抽選がズレる」症状が出る (wc2 のような負seedチャンクで発覚した)
3. `seed * 73856093 + ...` の混合は **32bit符号付きwrap** を再現する(`v%2**32` → `>=2**31` なら `-2**32`)
4. `Next(max)` は `int(Sample() * max)`、`Sample = InternalSample() / 2147483647.0`
5. 実験で乱数消費順を変えると地形が全体的にズレる(それ自体はOKだが「既存地形を保つ微調整」には使えない)

ASCII可視化の表示規則: 行=z座標(-5〜14)、列=x座標(0〜23)、`T`=木 `R`=岩 `H`=破壊不能岩 `P`=池 `-`=コリドー。

v2ノイズ方式のプロトタイプ・検証ツール: `Tools/terrain_noise_proto.py` (v1位置検証、ノイズ分布パーセンタイル、ASCII可視化、tier別実測密度)。実行: `python Tools\terrain_noise_proto.py`

## 駅まわりの生成・配置ルール (Phase 10-11)

- **駅サイズ**: プラットフォーム 2×1タイル (見た目 2×1m、中心=駅タイル)。x±1かつ站台z行のみ生成クリア
- **線路脇クリア**: 駅タイルx±2 かつ |wz-originZ|<=2 は従来通り常時空 (作業スペース)
- **zジッタ配置**: 站台zは候補 {originZ+2..+5} (ワールド8〜11) から決定的に選択。`ChunkManager.StationJitterOffset(k, seed)` が `ComputeTileTypeRaw` (クリア無視の素のタイプ) を候補ごとにスキャンし、破壊不能岩(type2)ゼロ→障害物最少の候補を採用。純粋関数なので全クライアント一致、同期不要。attemptは0固定でスキャン (attemptラダーは岩を減らす方向のみなので配置後に岩が増えない)
- **站台クリアは生成関数に組込み** (`IsInStationPlatform`): ジッタ確定zの站台タイルは `ComputeTileType` が -1 を返すので最初から何も生えない。マスクbit消去と違い、チャンク再生成での再出現・クライアント間ズレ・SFX暴発が構造的にない。`EnsurePond` も同チェックでスキップ
- **駅前stub線路**: 各駅に (stationX-1, 0) と (stationX, 0) の2枚を予め敷設 (`TrackManager.OwnerBuildStationStub`、撤去不可)。本線が隣接すると `ApplyTrack` のsuccessor連結で自動的にパスへ編入される
- **接続加速**: オーナーの TrainController が次駅の stub開始タイルの `IsOnPath` を監視し、接続中は `CurrentSpeed()×stationBoostMultiplier` (初期3倍、public調整可)。`[UdonSynced] stationBoost` でリモートの速度推定にも使用。列車同期は Manual sync + `syncInterval` (public、初期10s) 周期/イベント即時で、リモートはローカル推進+末端クランプ+Lerp補正

v1の旧値 (木34% / 岩16% / コリドー全チャンク) は「現行アルゴリズム仕様 (M2実装済み)」節を参照。

## 検討論点(別セッションで詰めたいこと)

1. **密度のゲーム体感**: 序盤の木7/岩4は多すぎ/少なすぎ? Unrailed原作はもう少し密。8人Co-opの採掘速度とのバランス
   - v2実測: tier0で43%/9.4個とv1(50%/11個)よりやや軽め。木の名目率を30→33%にすればv1並。原作寄せで密にするなら35-40%も視野
2. **池の配置ルール**: 1タイル単位だと「水たまり」感。隣接池同士を繋げる後処理(決定的にできる)を入れるか
   - **v2で解決**: ノイズのレベルセットなので池は自然に連結する。異方性(λx40m/λz13m)で「線路に沿った湖」になり、z全幅封鎖も防げる
3. **コリドー幅**: ±2mは線路1本+作業スペース。資源運搬の動線として狭くないか
   - **クローズ: コリドーは先頭2チャンク(最初の駅周辺)のみ残して撤廃**。以降は全zに障害物が出て、プレイヤーが採掘・ルーティングで切り開く原作方式。進路封鎖はBFS検証+attemptラダーで防止
4. **セル分割 vs 自由配置**: 現在は重なり防止のためセル固定。より自然な見た目にするならポアソンディスク的な配置(決定的に実装可能か要検討)
   - **セル維持で決定**。配置はv1互換を保ち、見た目の自然さはノイズのクラスタリングで担保する方針
5. **装飾レイヤ**: 草・花など「効果のない飾り」を別確率で混ぜるか(見た目の密度向上、プール数との相談)
   - v2なら独立した第4レイヤ(別layerConst)として追加するだけで既存判定に影響しない。乱数消費順問題は解消済み
6. **バイオームフック**: worldChunk→バイオーム判定(例: 5駅ごとに砂漠/雪)を `GenerateChunk` 冒頭に挟む拡張点の確認
   - v2なら「tier別しきい値テーブルをバイオーム別に持つ」または「バイオームノイズでオフセット/波長を変調」が挿入しやすい
7. **橋の価格設計**: 池敷設に木材1個でいいか(M3実装時)
8. **tierカーブの飽和が速すぎる問題(新規)**: **クローズ(M4b)**: 駅間隔30タイルに本決めし、tier8到達=240m=8駅。ペーシングシム(`Tools/pacing_sim.py`)で4人プレイの限界が3〜5駅(片手)〜12駅(両手)と分かり、cap到達地点がちょうど終盤と整合するため増分調整は不要と判断
9. **池・破壊不能岩のビジュアル(新規)**: **仮ビジュアルで一旦クローズ**。生成・コライダー・線路ブロックは実装済み(`ChunkManager.SetPoolVisual` が type 2/3 を切替)。見た目は暫定プリミティブなので、正式ビジュアルは論点11で管理
10. **z方向の「永久に空の車線」**: **クローズ: flat配置で解決**。候補2つを計測比較した:
    - wobble (v1ジッター + ハッシュ派生±150cm): 帯は消えるが旧ギャップ中心にピーク1割の窪みが残る (jz+δ が台形分布のため端しか届かない)。衝突 0.002/chunk
    - **flat (zをセルピッチ500cmでハッシュ全展開)**: 全行で均一 (窪みなし)、z範囲はv1と同一。衝突 0.07/chunk
    flatを採用し、C#移植・Unity 240スロット一致検証まで完了
11. **池・硬岩の正式ビジュアル(新規)**: 現在は仮ビジュアル(シーンビルダ生成のプリミティブ)。破壊不能岩=暗灰Cube 1.0×0.9×1.0 (`HardRockDark` マテリアル)、池=青平板 0.95×0.05×0.95 (`PondBlue` マテリアル)。正式化の方向性: 岩はメッシュ/岩肌表現、池は水面表現(透明度・揺らぎ・橋との視覚的一貫性)。木・岩ノードの正式ビジュアルとまとめてアートパスで扱う

## 既知の修正済みバグ

- **GetNodeAtTile のzオフセット**: `ntz = FloorToInt(lp.z)` (ワールドz) をトラックタイルzと直接比較していたが、TrackManager.origin.z=6 なのでタイルz = ワールドz - 6。ノード衝突判定がzに6タイルズレており、v1では木/岩の上に線路を敷けてしまっていた。`FloorToInt(lp.z - origin.z)` に修正済み (v2対応時)

## タイル規約 (整列修正で確定)

- 線路も地形も「**タイルNの中心 = 整数座標N**」で統一。ワールド→タイル変換は `FloorToInt(pos - origin + 0.5)`
- ノード(木/岩/硬岩/池)はタイル中心±ジッター範囲内に配置され、ノードのあるタイルは線路敷設ブロック、採掘枯渇後に敷設可能になる
- ツール(斧/ピッケル)側も衝突位置に `+0.5` してから `FloorToInt` で同一タイルにマップする
